# Feature Specification: 集成外部文件与数据存储

**Feature Branch**: `001-integrate-storage-services`  
**Created**: 2026-03-11  
**Status**: Draft  
**Input**: User description: "本地已经搭建了 filebrowser 和 mongo 服务，前者用于文件资源，后者用于其余业务数据，并且两类服务地址后续可在 app 中人为修改和配置。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 配置外部存储连接 (Priority: P1)

作为使用 HomeHoney 的家庭管理员，我希望在应用内查看、修改并保存文件服务和数据服务的连接配置，这样当本地地址、端口或部署环境变化时，我不需要重新打包应用也能继续使用。

**Why this priority**: 如果连接配置不能由用户调整，后续文件与数据外置的所有能力都会被环境变化阻塞，因此这是整项工作的基础价值。

**Independent Test**: 在应用中打开存储配置入口，修改两类服务地址并保存，重启应用后仍能读取到更新后的配置，并能基于新配置继续访问对应能力。

**Acceptance Scenarios**:

1. **Given** 应用已提供默认的文件服务与数据服务连接信息，**When** 用户在设置中修改任一服务地址并保存，**Then** 新配置会被持久保存并在后续启动时继续生效
2. **Given** 用户输入的连接信息不完整或格式明显无效，**When** 用户尝试保存，**Then** 应用会阻止保存并提示需要修正的内容
3. **Given** 用户已经更新连接配置，**When** 应用调用文件资源或业务数据能力，**Then** 应使用最新保存的配置而不是固定写死的地址

---

### User Story 2 - 统一管理文件性质资源 (Priority: P2)

作为管理家庭资料的用户，我希望保险合同、说明书等文件性质的资源统一存放在外部文件服务中，并且可以在应用里完成列表查看、信息获取、上传和下载，这样文件资产能够集中管理并与应用流程保持一致。

**Why this priority**: 文件性质资源是 HomeHoney 的核心内容之一。只有把这类资源统一接入外部文件存储，应用才能摆脱本地静态数据或单机限制，形成可持续管理的文件中心。

**Independent Test**: 准备至少一条保险合同或说明书记录，在应用中完成文件列表读取、详情信息查看、文件上传和文件下载，并确认这些操作都基于外部文件服务结果返回。

**Acceptance Scenarios**:

1. **Given** 外部文件服务中已有文件性质资源，**When** 用户进入资料模块，**Then** 应用能够展示这些资源的列表与基本信息
2. **Given** 用户正在新增或编辑一条文件性质资源，**When** 用户上传文件，**Then** 文件应被保存到外部文件服务并返回可用于后续访问的资源标识
3. **Given** 用户浏览某条文件性质资源详情，**When** 用户执行下载或打开原文件操作，**Then** 应用能够从外部文件服务获取对应文件内容
4. **Given** 某条文件性质资源已被删除或不可访问，**When** 用户尝试查看或下载，**Then** 应用应明确告知资源状态异常而不是展示错误内容

---

### User Story 3 - 管理非文件业务数据 (Priority: P3)

作为使用 HomeHoney 的家庭成员，我希望除了文件本体以外的其余业务数据都保存在外部数据服务中，并且在应用里支持新增、查询、修改和删除，这样提醒、设置、标签、备注及文件相关元数据等内容都能稳定持久化。

**Why this priority**: 文件接入只能解决资源存储问题，其余业务数据若不能外置并支持完整维护，应用仍无法形成真实可持续的数据管理能力。

**Independent Test**: 在应用中对一类非文件业务数据执行新增、列表查询、详情查看、修改和删除，关闭并重新打开应用后仍能看到最终结果。

**Acceptance Scenarios**:

1. **Given** 应用存在非文件业务模块，**When** 用户创建、编辑或删除这些业务数据，**Then** 变更应被持久保存到外部数据服务
2. **Given** 文件性质资源存在标题、分类、标签或其他非文件字段，**When** 用户更新这些字段，**Then** 相关业务信息应保存在外部数据服务并与文件资源保持关联
3. **Given** 外部数据服务中已存在业务记录，**When** 用户重新进入对应页面，**Then** 应用能够查询并展示最新数据状态

---

### Edge Cases

- 当文件服务地址或数据服务地址被修改为不可访问值时，应用应明确提示连接失败，并保留用户再次修正配置的入口
- 当文件上传成功但相关业务记录保存失败时，系统应向用户明确说明状态不一致，并提供可追踪或可恢复的结果反馈
- 当业务记录已删除但外部文件仍存在时，应用不应继续在正常列表中展示该记录
- 当外部文件已不存在但业务记录仍保留时，应用应将该记录标记为文件不可用，而不是误导用户文件可正常下载
- 当外部服务暂时不可用时，应用应避免把空结果误判为“没有数据”
- 当用户切换到新的服务地址后，应用应基于新配置读取数据，而不是混用旧连接结果

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供可由用户查看、修改和保存的文件服务连接配置
- **FR-002**: 系统必须提供可由用户查看、修改和保存的数据服务连接配置
- **FR-003**: 系统必须在应用重启后继续使用用户最近一次成功保存的连接配置
- **FR-004**: 系统必须在保存配置前校验必填连接信息是否完整且格式可接受，并对无效输入给出明确提示
- **FR-005**: 系统必须将保险合同、说明书及其他文件性质资源的文件本体统一存放到外部文件服务中
- **FR-006**: 系统必须支持对文件性质资源执行列表获取、信息读取、上传和下载操作
- **FR-007**: 系统必须让用户能够在应用内识别文件性质资源的可用状态，包括正常、缺失或不可访问等情况
- **FR-008**: 系统必须将除文件本体以外的业务数据持久保存到外部数据服务中
- **FR-009**: 系统必须支持非文件业务数据的新增、查询、修改和删除操作
- **FR-010**: 系统必须为文件性质资源维护与业务数据之间的关联关系，使用户能够从业务记录定位到对应文件资源
- **FR-011**: 系统必须确保读取文件资源时使用文件服务，读取非文件业务数据时使用数据服务，不得混淆职责边界
- **FR-012**: 当任一外部服务访问失败、超时或返回异常时，系统必须向用户展示可理解的失败反馈，而不是静默失败
- **FR-013**: 系统必须允许团队在不重新发布应用的前提下切换外部文件服务和外部数据服务的连接目标
- **FR-014**: 系统必须保持现有核心业务流程可继续完成，包括资料浏览、文件查看以及非文件业务信息维护

### Key Entities *(include if feature involves data)*

- **存储配置**: 用户保存的外部连接信息，区分文件服务配置与数据服务配置，决定应用后续访问目标
- **文件性质资源**: 例如保险合同、说明书等以文件本体为核心的业务资源，包含展示字段、分类信息与外部文件引用
- **业务数据记录**: 除文件本体外需要持久化的结构化数据，例如提醒、标签、备注、设置项或文件资源的描述信息
- **文件引用关系**: 连接业务记录与外部文件资源的关联信息，用于从应用记录定位到具体文件
- **同步结果**: 一次创建、更新或删除操作在外部文件服务和外部数据服务中的最终处理状态，用于向用户反馈是否一致完成

## Assumptions

- 当前团队已具备可用的外部文件服务与外部数据服务实例，本次工作重点是让应用接入并使用它们
- 用户提供的连接信息代表当前默认接入目标，但后续需要允许在应用中调整
- 文件本体与结构化业务数据采用分离存储策略：文件本体放在外部文件服务，除文件本体外的其余信息放在外部数据服务
- 文件性质资源仍保留现有业务分类方式，例如保险合同、说明书等，只改变其底层存储位置与访问方式
- 本次工作范围包含现有业务数据的持久化接入与日常维护能力，不强制要求历史数据自动迁移，除非后续规划另行补充
- 外部服务的鉴权方式沿用现有可用部署方式；本次规范聚焦在地址配置、资源读写与数据职责划分

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户能够在 2 分钟内完成文件服务和数据服务连接配置的查看、修改与保存，并且无需重新安装或重新发布应用
- **SC-002**: 100% 的文件性质资源文件读写操作都通过外部文件服务完成，不再依赖应用内置或本地临时存储作为正式来源
- **SC-003**: 100% 的非文件业务数据维护操作都能完成新增、查询、修改和删除，并在应用重启后保持结果一致
- **SC-004**: 在外部服务可用的前提下，用户对文件性质资源执行列表、上传、详情读取和下载的成功率达到 100%
- **SC-005**: 当外部服务不可达或返回异常时，100% 的失败场景都向用户展示明确错误反馈，而不是表现为无响应或空白数据
- **SC-006**: 团队在切换服务地址后，无需修改应用包体即可继续完成文件资源访问和非文件数据维护两类核心流程

# Research: 通过后端 API 托管存储集成

## 决策 1：新增独立的 ASP.NET Core Web API 项目，而不是继续在移动端直连下游服务

- **决策**：新增 `HomeHoney.Api` 项目作为移动端唯一业务入口，移动端后续只连接后端 API，不再直接连接 FileBrowser 或 MongoDB。
- **理由**：用户已明确要求移动端与 FileBrowser/Mongo 之间增加一层 API 服务。这样可以把下游连接、异常分类、DTO 映射、聚合逻辑和后续安全治理统一收敛到服务端。
- **考虑过的替代方案**：
  - **继续让移动端直连 FileBrowser 与 MongoDB，只做少量封装**：被否决，因为不能满足“移动端不想直接连接底层服务”的核心要求。
  - **拆成多个独立后端服务**：被否决，因为当前业务规模更适合单一后端项目的模块化单体，避免过早引入服务拆分复杂度。

## 决策 2：采用“模块化单体”后端结构，而不是将全部逻辑堆在控制器层

- **决策**：`HomeHoney.Api` 内部按 `Application`、`Infrastructure`、`Contracts`、`Controllers/Endpoints` 分层；业务按文档、协作、偏好、提醒、搜索、存储配置等领域拆分。
- **理由**：当前移动端已有 `DocumentCatalogService`、`FamilyCollaborationService`、`ReminderCenterService`、`SearchIndexService` 等业务边界，迁移到后端时应保留这些领域划分，避免 API 控制器直接操作 Mongo 或 FileBrowser。
- **考虑过的替代方案**：
  - **只建一个简单 Web API 项目，把所有逻辑放到控制器**：被否决，因为难以承接现有聚合逻辑、测试边界和后续扩展。
  - **立即拆成单独的 documents-api / collaboration-api / search-api**：被否决，因为超出当前规模需求，不利于快速完成迁移。

## 决策 3：移动端只保存后端服务地址；下游存储配置由后端拥有

- **决策**：移动端本地仅保存后端服务地址及必要的用户偏好/敏感信息；FileBrowser 与 MongoDB 的真实连接信息由后端管理。如果仍需要运行时修改下游目标，也通过后端管理接口完成。
- **理由**：这能彻底消除移动端对下游服务拓扑和敏感连接串的认知，符合“移动端只连后端”的目标，同时减少密钥暴露面。
- **考虑过的替代方案**：
  - **移动端继续保存 FileBrowser 与 Mongo 连接信息，再由后端透传使用**：被否决，因为移动端仍会感知下游拓扑，与目标相冲突。
  - **彻底取消任何可编辑配置**：被否决，因为现有产品能力要求连接目标可在运行时调整。

## 决策 4：按业务域设计 API，而不是暴露通用存储接口

- **决策**：后端 API 以业务域分组，例如 `documents/insurance`、`documents/manuals`、`collaboration/fridge-notes`、`collaboration/memos`、`reminders`、`search`、`preferences/me`、`admin/storage`。
- **理由**：用户操作的是保险、说明书、冰箱贴、备忘录等业务对象，不是 Mongo 集合或文件服务资源。按业务分组能够稳定移动端契约，也能隐藏底层存储结构。
- **考虑过的替代方案**：
  - **暴露通用 `/files` 与 `/records` 接口让移动端自行拼装**：被否决，因为会把聚合职责重新推回移动端。
  - **直接把 Mongo 集合和 FileBrowser 资源路径映射成 REST 路由**：被否决，因为会泄露底层实现细节。

## 决策 5：文件上传下载继续由后端代理，并采用流式处理

- **决策**：文件上传和下载均通过后端代理到 FileBrowser，下行与上行都采用流式转发；移动端不直接获取 FileBrowser 原始 URL。
- **理由**：当前目标是让后端成为唯一集成点。流式代理可以避免大文件完整落入内存，同时保持下游文件服务细节对移动端不可见。
- **考虑过的替代方案**：
  - **后端只返回预签名链接或重定向，让移动端直连文件服务**：当前阶段被否决，因为会破坏“移动端只连后端”的架构边界。
  - **后端完整缓存文件再返回移动端**：被否决，因为会增加内存与磁盘压力，也与现有“无本地业务文件持久化”边界冲突。

## 决策 6：跨 FileBrowser 与 MongoDB 的写操作按编排工作流处理，而不是假设强事务

- **决策**：文件上传、删除与文档元数据更新由后端应用服务编排，明确维护成功、失败、部分成功和待修复状态。
- **理由**：FileBrowser 与 MongoDB 没有共享事务边界。当前移动端已开始建模 `IntegrityStatus`、`SyncMessage` 和 `FileAvailabilityStatus`，后端应接管这些状态规则并对移动端返回统一结果。
- **考虑过的替代方案**：
  - **把双写失败统一简化为通用错误**：被否决，因为不能支持可见的不一致状态和后续补偿。
  - **要求下游实现分布式事务**：被否决，因为不现实，也超出当前范围。

## 决策 7：搜索、提醒和资料详情改为后端聚合读模型

- **决策**：后端负责计算提醒中心、全局搜索以及资料详情页所需的聚合结果，移动端只消费单一业务响应。
- **理由**：现有移动端的 `ReminderCenterService` 与 `SearchIndexService` 已承担跨资料与协作模块的聚合职责，这些逻辑更适合服务端统一处理，以减少移动端多次往返与自行组装数据。
- **考虑过的替代方案**：
  - **继续让移动端分别请求多个后端接口再自己聚合**：被否决，因为会增加网络往返与页面层复杂度。
  - **只迁移 CRUD，不迁移聚合读模型**：被否决，因为无法彻底达成“移动端只处理界面”的目标。

## 决策 8：后端契约使用显式 DTO 和 OpenAPI，而不是直接复用 MAUI 模型

- **决策**：后端对外定义独立的请求/响应 DTO，并以 OpenAPI 文档作为契约基线；不直接把移动端内部模型暴露为公共 API Schema。
- **理由**：MAUI 模型包含 UI 语义、默认值与实现细节，直接暴露会造成客户端与服务端的演进耦合。显式 DTO 也更适合做契约测试与版本管理。
- **考虑过的替代方案**：
  - **前后端共享同一组模型类**：被否决，因为会让 UI 模型演化直接破坏 API 兼容性。
  - **只靠代码阅读，不维护显式接口文档**：被否决，因为此特性会新增完整后端边界，需要清晰契约。

## 决策 9：后端测试分为应用层单测、API 集成测试、下游适配器测试

- **决策**：新增 `HomeHoney.Api.Tests`，使用 `WebApplicationFactory` 验证 HTTP 路由、序列化、`ProblemDetails` 与配置注入；同时对 FileBrowser/Mongo 适配器和编排逻辑补充单元与集成测试。
- **理由**：本次改造的最大风险在于接口契约漂移、聚合逻辑行为变化以及下游失败路径处理，单纯依赖现有 MAUI 单元测试不足以覆盖这些问题。
- **考虑过的替代方案**：
  - **继续只保留移动端测试项目**：被否决，因为无法充分覆盖 Web API 路由与服务端依赖注入行为。
  - **只做端到端手测**：被否决，因为过于脆弱，且不能稳定防止回归。

  ## 决策 10：迁移过程中先复用现有领域模型打通主链路，再逐步收敛到独立 DTO 与仓储

  - **决策**：当前迭代优先把移动端到后端、后端到 FileBrowser/Mongo 的读写主链路打通，允许 `HomeHoney.Api` 在过渡期复用现有 `HomeHoney` 领域模型；随后再按计划收敛为显式 DTO、映射器与仓储层。
  - **理由**：用户当前更关注“移动端不再直连下游”和“文件/非文件核心业务先通过后端完成”的结果。先打通主链路可以更快验证架构方向，并用 API 集成测试固定关键行为。
  - **考虑过的替代方案**：
    - **在打通任何端到端路径前就完整重建 DTO、仓储和应用服务分层**：被否决，因为实现跨度更大，反馈周期更慢，不利于先验证后端代理架构是否满足核心业务诉求。
    - **长期维持共享模型，不再做契约收敛**：被否决，因为会让移动端内部模型持续泄漏到公共 API，后续演进成本过高。

  ## 决策 11：移动端设置页仅暴露后端 API 地址，并隐藏内置默认地址

  - **决策**：移动端“外部存储”设置页不再提供 FileBrowser/Mongo 下游字段，也不再在本地保存或展示下游连接配置；仅保留后端 API 地址覆盖能力，并在未覆盖时使用内置默认地址 `http://localhost:7080` 且不直接显示该值。
  - **理由**：移动端继续展示或保存下游配置，会削弱“移动端只连接后端”的信任边界，也会把不必要的连接信息暴露给终端设备。隐藏内置默认地址则能减少误抄、误泄露和界面上的无意义重复暴露。
  - **考虑过的替代方案**：
    - **继续让移动端显示后端默认地址和下游配置只读信息**：被否决，因为仍会向终端用户暴露本不需要关注的拓扑细节。
    - **完全不允许覆盖后端地址**：被否决，因为本地调试和自托管场景仍需要保留后端入口的可切换能力。

## 实施后约束结论

  - 移动端保留 Preferences / SecureStorage，但其“外部存储设置”语义已进一步收敛为“仅连接 HomeHoney 后端服务”；如需下游配置管理，应通过后端管理接口或服务端配置承接。
- 后端成为新的信任边界，应在实现阶段补充 HTTPS、结构化日志、健康检查、配置校验和统一错误输出。
- 当前 `.specify/memory/constitution.md` 的“离线优先 + 本地 SQLite/本地文件系统”条款与本仓库实际已采用的远端存储边界冲突，需在正式实现前以章程修订或例外说明方式解决。

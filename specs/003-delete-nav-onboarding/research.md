# Research: 资料删除、返回导航与首次引导优化

## 决策 1：删除采用“显式确认后执行”的本地服务模式

- **决策**：保险、说明书和冰箱贴的删除由现有本地服务层提供显式删除方法，页面侧在执行前展示确认操作，而不是点击即删。
- **理由**：当前应用以本地数据和移动端触控为主，误触风险高；显式确认可以在不引入复杂撤销机制的前提下，显著降低误删概率。
- **考虑过的替代方案**：
  - **点击即删**：被否决，因为详情页和编辑页的主操作区域较集中，触控误删风险过高。
  - **删除后再提供撤销**：被否决，因为当前服务层是轻量本地实现，先增加确认更符合当前复杂度控制。

## 决策 2：返回导航采用“页面层级返回”而非依赖浏览器历史

- **决策**：二级及更深页面统一提供明确返回按钮，并按业务层级返回到上一级页面，例如详情返回列表、编辑返回详情或列表、设置子页返回设置首页。
- **理由**：MAUI Blazor Hybrid 虽有导航历史，但用户心智更依赖“当前在什么模块下”。显式层级返回比单纯依赖浏览历史更稳定、更符合移动端导航预期。
- **考虑过的替代方案**：
  - **统一调用浏览器后退**：被否决，因为从搜索结果、首页摘要、深链进入时，历史栈不一定等于期望业务上一级。
  - **所有深层页面都只返回首页**：被否决，因为会打断多层操作连续性。

## 决策 3：返回入口优先放在页面头部动作区

- **决策**：所有超过一级的页面在标题区域提供统一位置的返回按钮，和主要动作（如编辑、保存、删除）一起组成顶部动作区。
- **理由**：顶部动作区已经是当前页面结构中最稳定、最易发现的位置；用户不需要重新学习不同页面的返回入口位置。
- **考虑过的替代方案**：
  - **把返回按钮放在底部表单区**：被否决，因为用户在阅读详情时需要先看到返回路径。
  - **只用系统手势返回**：被否决，因为不同平台一致性不足，且不利于桌面/模拟器场景。

## 决策 4：首次引导自动出现与“帮助回看引导”必须分离

- **决策**：自动引导只由“是否完成首次引导”状态控制；帮助或设置中的引导回看入口只负责展示内容，不会重置默认启动规则。
- **理由**：用户明确要求首次自动出现、后续不再自动出现。若把“回看引导”与“重置首次引导状态”绑定，会破坏长期使用体验。
- **考虑过的替代方案**：
  - **回看引导即重置首次引导状态**：被否决，因为会导致下次启动再次强制进入引导。
  - **完全移除回看入口**：被否决，因为帮助入口仍有价值，只是不应改变启动逻辑。

## 决策 5：删除后的回流页面优先回到模块列表

- **决策**：删除成功后默认返回所属模块列表页；若删除发生在编辑页，同样回流到列表页或模块主页，而不是留在详情页。
- **理由**：被删除对象的详情页已经失效，返回列表是最稳定且最可继续操作的上下文。
- **考虑过的替代方案**：
  - **删除后停留原页并提示不存在**：被否决，因为会形成死页面。
  - **删除后统一回首页**：被否决，因为会打断当前模块操作流程。

## 决策 6：本特性不新增数据实体，优先扩展现有模型与服务契约

- **决策**：继续复用既有 `InsuranceRecord`、`ManualRecord`、`FridgeNote` 与 `UserPreference`，仅扩展服务方法和页面行为，不引入新的持久化实体。
- **理由**：本次需求核心是生命周期补足和导航体验完善，不需要额外复杂建模。
- **考虑过的替代方案**：
  - **新增删除日志或导航状态实体**：被否决，因为当前需求并未要求审计或复杂回溯，过度设计会增加实现成本。

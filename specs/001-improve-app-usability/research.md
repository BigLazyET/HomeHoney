# Research: Improve App Usability

## 决策 1：新增/编辑表单采用“空白起步 + 语义提示”，而不是预填示例值

- **决策**：说明书、保险、备忘录、冰箱贴的新增表单统一移除误导性默认内容；对必须由用户主动确认的字段，改为显示占位提示、帮助文案或空状态说明。
- **理由**：当前模型层存在枚举、日期、颜色等默认值，如果直接映射到 UI，容易让用户误以为这些值已经被确认，从而生成错误数据。对移动端录入场景而言，“我还没选”比“系统替我选了一个看似合理的值”更安全。
- **考虑过的替代方案**：
  - **保留现有默认值，仅补充说明文字**：被否决，因为用户仍可能忽略提示，直接提交错误默认数据。
  - **每个页面各自定义默认值策略**：被否决，因为会造成行为不一致，增加维护成本。

## 决策 2：用统一的页面状态契约处理空状态、失败状态和重试状态

- **决策**：搜索、提醒和资料列表采用统一的可重试视图状态模型，至少覆盖 `Loading`、`Ready`、`Empty`、`Error`、`Retrying` 五类状态，并在页面内提供显式重试入口。
- **理由**：当前仓库已经有 `StatusBanner` 和 `EmptyState` 等共享组件，继续扩展统一状态契约可以避免每个页面自行拼装反馈逻辑，也能确保“空数据”和“加载失败”被清晰区分。
- **考虑过的替代方案**：
  - **继续依赖页面刷新或重新进入页面恢复**：被否决，因为用户恢复成本高，且不利于移动端体验。
  - **每个列表页独立实现一套提示和重试逻辑**：被否决，因为容易造成文案、按钮位置和行为不一致。

## 决策 3：附件区域直接消费现有文件元数据字段，并补充显式缺省语义

- **决策**：附件区域展示以现有 `PrimaryFile` / `FileResource` 数据为单一来源，重点使用 `FileName`、`SizeBytes`、`LastSyncedAt` 和可用性状态，并在元数据不完整时显示明确的缺省说明。
- **理由**：仓库现有模型已经具备文件名、大小、上传时间、最后同步时间与可用性状态字段，优先复用可减少额外契约扩张。特性重点是“让用户看见并理解附件状态”，而不是再引入新的冗余文件摘要模型。
- **考虑过的替代方案**：
  - **为附件展示单独新增一套后端接口或独立 DTO**：被否决，因为当前所需信息已存在于现有文档模型中。
  - **只有在下载时再动态获取文件信息**：被否决，因为用户需要在点击前就判断文件是否值得下载。

## 决策 4：输入健壮性采用“页面即时校验 + 服务边界兜底”双层策略

- **决策**：表单交互层负责即时提示必填、空白字符和明显无效输入；服务/API 边界继续负责最终兜底校验与标准化，且无论哪一层拦截，都必须保留用户已输入的有效内容。
- **理由**：只在页面层校验会让脏数据仍有机会穿透到服务层；只在服务层校验则会让用户在点击保存后才感知问题，体验滞后。双层校验最符合移动端高频录入场景。
- **考虑过的替代方案**：
  - **只做前端即时校验**：被否决，因为无法完全防止服务边界被无效数据击穿。
  - **只做后端/API 校验**：被否决，因为对用户来说反馈过晚，且会增加无意义网络往返。

## 决策 5：手动重试仅作用于读取型页面，不改变既有业务语义

- **决策**：本次重试能力限定在搜索、提醒和资料列表等读取型页面；重试行为只重新发起当前读取请求，不引入新的数据写入、副作用或导航变化。
- **理由**：用户提出的是“页面层恢复能力”，而非新的后台任务机制。将范围限定为读取型页面，可以显著改善失败后的可恢复性，同时保持实现边界清晰。
- **考虑过的替代方案**：
  - **把所有保存、删除、上传、下载都统一抽象成自动重试机制**：被否决，因为会改变原有业务幂等性和失败语义，超出本次范围。
  - **全应用统一自动后台重试**：被否决，因为会削弱用户对当前状态的感知，不利于明确反馈。

## 决策 6：Mongo 索引按“现有排序/筛选路径 + 近期待检索字段”统一引导，而不是等性能问题暴露后再零散补丁

- **决策**：为现有 Mongo 集合建立统一索引初始化机制，优先覆盖当前代码中已经稳定存在的排序与筛选字段，并为搜索相关文本字段建立可扩展的索引策略。
- **理由**：当前后端读取中已经存在明确的排序/筛选模式，例如保单按到期日、说明书按空间、冰箱贴按置顶/截止时间、备忘录按截止时间、偏好按单记录读取。提前把这些模式转化为索引策略，可以减少数据量增长后的明显退化，并为后续把搜索从内存聚合下推到数据库创造条件。
- **考虑过的替代方案**：
  - **暂不做任何索引，等线上退化后再补**：被否决，因为补救成本更高，也与用户明确提出的要求不符。
  - **立即全面重写为数据库原生全文检索方案**：被否决，因为当前搜索仍是后端聚合读取，直接重写搜索引擎会扩大范围。

## 决策 7：代码审查范围聚焦于本特性影响链路及其邻近服务，而不是全仓库重构

- **决策**：本次“查漏补缺”以受影响的表单、列表、附件详情、相关服务和后端仓储/索引初始化为中心，重点修复空值、异常状态残留、默认值污染和反馈不一致问题。
- **理由**：用户要求主动 review 并修正问题，但当前最能产生业务价值的范围，是与新交互要求直接相连的链路。聚焦邻近模块可以在保证覆盖度的同时控制实施风险。
- **考虑过的替代方案**：
  - **对整个仓库展开无边界重构**：被否决，因为超出本特性范围，也不利于稳定交付。
  - **完全只改 UI，不碰服务和后端**：被否决，因为部分问题（尤其是附件元数据和索引）必须穿透到后端边界才能闭环。

## 研究结论

- 无 `NEEDS CLARIFICATION` 项目残留。
- 本特性应维持现有“移动端仅连接后端 API”的边界。
- 设计重点应放在统一状态模型、输入健壮性、附件可见性和索引初始化，而不是扩大为架构重写。

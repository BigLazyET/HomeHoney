# Research: 升级到 .NET 10

## 决策 1：采用“统一版本基线一次性切换”，而不是局部逐项目升级

- **决策**：先统一更新 SDK 锁定与所有项目目标框架，再集中修复编译、测试和平台兼容问题，而不是只先升级主应用或测试工程中的某一部分。
- **理由**：官方升级指导指出，升级到新 .NET 版本的核心步骤是同步更新项目的 `TargetFramework` / `TargetFrameworks`，随后用新 SDK 构建并修正暴露出的差异。对当前双项目方案而言，若只升级单一项目，最容易产生 SDK、TFM、MAUI 工作负载和测试宿主之间的不一致。
- **考虑过的替代方案**：
  - **先只升级 `global.json`**：被否决，因为这只能切换本地 SDK 选择，不能保证解决方案实际面向 .NET 10。
  - **先只升级测试项目到 .NET 10**：被否决，因为测试项目直接引用主应用项目，会放大跨项目版本不一致问题。

## 决策 2：目标框架统一升级到 `net10.0` 与 `net10.0-*` 族，而不是继续停留在 `net9.0` 并仅依赖新 SDK

- **决策**：应用项目将从 `net9.0` / `net9.0-android` / `net9.0-ios` / `net9.0-maccatalyst`（以及条件 Windows TFM）迁移到对应的 `net10.0` / `net10.0-*`，测试项目迁移到 `net10.0`。
- **理由**：官方 TFM 文档明确给出了 `net10.0`、`net10.0-android`、`net10.0-ios`、`net10.0-maccatalyst`、`net10.0-windows` 的连续命名规则。若仅使用 10.0 SDK 继续构建 `net9.0`，并不能实现“升级到 .NET 10”的用户目标，只能算是在新 SDK 下继续面向旧目标框架。
- **考虑过的替代方案**：
  - **仅安装 10.0 SDK、保持 `net9.0` 目标框架**：被否决，因为这不满足功能要求中的统一升级目标。
  - **先升级基础 `net10.0`，延后 OS-specific TFM**：被否决，因为 MAUI 构建高度依赖 OS-specific TFM，一旦拆开升级，验证路径会更加复杂。

## 决策 3：保持当前平台最低支持范围不变，除非升级过程暴露出明确的官方强制要求

- **决策**：默认保留当前项目中声明的 iOS 16、Android API 33、Mac Catalyst 15 与 Windows 最低版本约束，只在 .NET 10 / MAUI 10 明确要求更高下限时才调整。
- **理由**：规范目标强调升级后保持交付连续性，而不是顺带改变产品平台策略。研究结果显示 .NET 10 / MAUI 10 的新能力包含更高 Android API 支持和质量改进，但这并不自动等于必须提升当前业务支持下限。
- **考虑过的替代方案**：
  - **随升级一并提升所有平台最低版本**：被否决，因为这会扩大范围并改变产品支持边界。
  - **不检查平台最低版本兼容性**：被否决，因为多平台交付连续性是本特性的独立验收目标。

## 决策 3.1：将 Xcode 26.2 与 Java 17+ 作为当前平台验证前提记录下来

- **决策**：在升级文档与验收契约中明确记录当前环境观测到的工具链前提：iOS / Mac Catalyst 的 .NET 10 构建需要 Xcode 26.2，Android 的 manifest merger 需要 Java 17+。
- **理由**：本次实际验证显示，解决方案在 `net10.0` 与测试项目上可通过，但 iOS / Mac Catalyst 构建受 Xcode 26.0 限制，Android 构建受 Java 11 限制。将其记录为环境前提，能满足“失败可定位”的规范目标。
- **考虑过的替代方案**：
  - **忽略这些失败并视为代码问题**：被否决，因为失败信息明确指向外部工具链版本。
  - **通过降低目标框架规避要求**：被否决，因为这会破坏升级到 .NET 10 的核心目标。

## 决策 4：将 `restore` / `build` / `test` / 工作负载恢复视为升级验收主链路

- **决策**：升级成功的主要验证链路定义为：确认 .NET 10 SDK 可用 → 恢复 MAUI 工作负载 → 解决方案构建通过 → 测试项目通过 → 核心页面抽样验收。
- **理由**：官方升级文档明确指出，升级源代码后应使用新 SDK 重新构建，并在需要时执行 `dotnet workload restore`。当前环境已安装 .NET 10 SDK，但 MAUI 工作负载仍停留在 9.x 清单，因此必须把工作负载恢复纳入主链路。对当前仓库来说，构建与测试已经是现有最稳定的自动化门禁，因此最适合作为升级完成的主链路。
- **考虑过的替代方案**：
  - **只做解决方案构建，不跑测试**：被否决，因为规范明确要求测试工程连续可用。
  - **只做手动冒烟，不做 CLI 验证**：被否决，因为无法稳定判断升级是否真正完成。

## 决策 5：优先修复由 .NET 10 兼容性和分析规则触发的差异，不主动引入架构重构

- **决策**：如果 .NET 10 引入新的行为差异、分析器结果或平台兼容警告，仅对受影响位置做最小必要修复；不将本次升级扩大为 MVVM 改造、存储层重写或页面架构重组。
- **理由**：.NET 10 带来新的 breaking changes 和 SDK/分析器行为，但当前需求核心是“升级并保持连续可用”。保持变更原子性有助于快速定位升级问题，也符合规范中“避免引入与本次目标无关的功能性行为变更”。
- **考虑过的替代方案**：
  - **借机进行大规模架构重构**：被否决，因为会掩盖升级本身的风险来源。
  - **完全忽略 breaking changes 清单**：被否决，因为这会把问题留到构建或运行时才暴露。

## 决策 6：文档、前置条件与验收脚本必须与代码升级同步交付

- **决策**：在升级工程文件和验证通过后，同步更新 `README.md`、规范 quickstart 与契约文档中的 SDK 前置条件、目标框架、构建命令和验证说明。
- **理由**：用户故事 3 明确要求降低后续协作成本。若只升级代码而不更新仓库说明，团队成员仍会在旧版 SDK 前提下复现失败。
- **考虑过的替代方案**：
  - **先完成代码升级，文档以后补**：被否决，因为这会导致仓库短时间内处于“代码和说明不一致”的状态。
  - **仅在 PR 描述中说明升级事项**：被否决，因为长期协作需要仓库内文档成为单一可信来源。

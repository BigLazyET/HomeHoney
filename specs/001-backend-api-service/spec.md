**Feature Branch**: `001-backend-api-service`  
**Created**: 2026-03-11  
**Status**: Draft  
**Input**: User description: "更改：移动端不想直接连接filebrowser和mongo，需要在移动端与fb，mongo之间添加一层api服务，所以需要新建一个homehoney.api项目，请用.net webapi技术框架实现；将目前移动端与fb，mongo交互的逻辑放到backend api项目中去，并按照业务创建对应的api接口。这是一项繁重的工作，请务必考虑全面和完美实现"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 统一通过后端访问业务能力 (Priority: P1)

作为 HomeHoney 的移动端用户，我希望应用只连接一个统一的后端服务来完成资料、提醒、备忘录和设置相关操作，而不是分别直接连接多个底层存储服务，这样移动端接入更稳定，后续部署与维护也更简单。

**Why this priority**: 这是整项调整的核心价值。如果移动端仍直接连接底层存储，本次改造的主要目标就没有达成，后续所有文件与数据能力也无法真正完成架构收敛。

**Independent Test**: 将移动端配置为仅连接后端服务后，完成一次资料列表读取和一次非文件数据读取，且移动端侧不再需要直接配置或访问底层存储协议即可交付最小价值。

**Acceptance Scenarios**:

1. **Given** 移动端已连接到可用的后端服务，**When** 用户进入资料、提醒或协作模块，**Then** 应用能够通过该后端服务读取所需业务结果
2. **Given** 移动端原本存在直连底层存储的调用路径，**When** 本特性完成后用户继续使用核心模块，**Then** 这些操作应全部改由后端服务承接，而不是继续由移动端直接访问底层存储
3. **Given** 后端服务地址发生变化，**When** 用户在应用中更新连接目标，**Then** 移动端后续请求应切换到新的后端服务地址并继续工作

---

### User Story 2 - 通过后端统一管理文件性质资源 (Priority: P2)

作为管理家庭文档的用户，我希望保险合同、说明书等文件性质资源由后端统一提供列表、详情、上传、下载和状态识别能力，这样移动端不需要理解底层文件服务的细节，也能稳定完成文件业务流程。

**Why this priority**: 文件资源是应用的核心内容。只有把文件相关交互收敛到后端，移动端才能摆脱对底层文件服务协议和异常处理的直接依赖。

**Independent Test**: 在移动端仅连接后端服务的前提下，完成一条保险或说明书记录的文件列表读取、文件上传和文件下载，即可独立证明该故事成立。

**Acceptance Scenarios**:

1. **Given** 用户浏览保险或说明书模块，**When** 页面请求文件性质资源列表或详情，**Then** 后端应返回移动端可直接消费的业务结果
2. **Given** 用户为保险或说明书记录上传文件，**When** 上传完成，**Then** 用户能够在移动端看到该文件已与对应业务记录建立关联
3. **Given** 某文件资源缺失、不可访问或状态异常，**When** 用户查看详情或尝试下载，**Then** 后端应返回明确的状态反馈，供移动端展示可理解的异常信息

---

### User Story 3 - 通过后端统一管理非文件业务数据 (Priority: P3)

作为家庭成员，我希望冰箱贴、备忘录、提醒、偏好和文档元数据等非文件业务数据也统一通过后端服务完成新增、查询、修改和删除，这样移动端只处理业务界面，不再承担底层数据访问与聚合职责。

**Why this priority**: 如果只有文件流程迁移到后端，而非文件业务仍由移动端直连底层数据服务，系统仍会保留双套集成方式，架构目标无法完整实现。

**Independent Test**: 在移动端仅连接后端服务的情况下，对至少一类非文件业务数据完成新增、查询、修改、删除，并在重新打开应用后看到一致结果。

**Acceptance Scenarios**:

1. **Given** 用户在冰箱贴、备忘录、提醒或偏好页面执行增删改查，**When** 操作提交，**Then** 后端应负责完成业务处理并返回结果给移动端
2. **Given** 文档元数据与文件状态需要联合展示，**When** 用户进入相关页面，**Then** 后端应返回已按业务语义整合好的结果，而不是要求移动端自己拼装多来源数据
3. **Given** 底层数据服务短暂失败或返回异常，**When** 用户访问非文件业务模块，**Then** 移动端应收到可解释的失败反馈，而不是暴露底层服务细节

---

### Edge Cases

- 当后端服务可访问但其下游文件或数据服务不可用时，系统应向移动端返回明确的业务失败状态，而不是无响应或模糊错误
- 当文件上传成功但相关业务记录更新失败时，系统应保留可追踪的不一致状态，便于用户识别和后续修复
- 当移动端仍保留旧的直连调用入口时，系统应避免新旧两套路径混用导致的数据来源不一致
- 当后端服务地址被修改为不可访问值时，用户仍应能够重新进入连接设置并修正配置
- 当后端返回的数据结构缺少关键字段时，移动端不应因原始格式变化而直接崩溃
- 当同一业务记录同时涉及文件状态与结构化数据状态时，系统应保证用户看到的是同一次业务操作对应的统一结果说明

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须新增一个独立的后端服务层，用于承接移动端与底层文件服务、底层数据服务之间的全部业务交互
- **FR-002**: 移动端必须能够通过单一后端服务地址访问现有核心业务能力，而不再直接访问底层文件服务或底层数据服务
- **FR-003**: 系统必须保留并迁移现有核心业务能力，包括资料浏览、文件上传下载、提醒查看、协作数据维护和偏好保存
- **FR-004**: 系统必须为保险合同、说明书等文件性质资源提供按业务划分的后端接口，覆盖列表、详情、上传、下载、状态识别与关联维护
- **FR-005**: 系统必须为冰箱贴、备忘录、提醒、偏好以及文档元数据等非文件业务数据提供按业务划分的后端接口，覆盖新增、查询、修改和删除
- **FR-006**: 后端服务必须负责屏蔽底层文件服务与底层数据服务的连接细节、数据映射和异常分类，移动端不得再承担这些职责
- **FR-007**: 系统必须允许移动端继续通过应用内配置切换其所连接的后端服务目标，并在重启后继续使用最近一次成功保存的连接
- **FR-008**: 如果业务仍要求可调整底层文件服务或底层数据服务目标，系统必须通过后端能力完成该配置读写，而不是让移动端直连下游服务
- **FR-009**: 后端返回给移动端的结果必须是面向业务语义的稳定数据，而不是要求移动端理解底层存储的原始协议格式
- **FR-010**: 当后端与其下游服务之间发生超时、认证失败、资源缺失或部分成功等情况时，系统必须向移动端返回明确且可展示的结果说明
- **FR-011**: 系统必须保证文件本体仍通过文件服务管理，结构化业务数据仍通过数据服务管理，但这一职责划分应由后端统一承接
- **FR-012**: 系统必须支持将现有移动端中的存储访问逻辑迁移到后端服务中，并确保业务行为在迁移后保持一致
- **FR-013**: 系统必须为搜索、提醒和资料详情等需要聚合多类数据的场景提供后端整合结果，减少移动端多次往返和自行组装
- **FR-014**: 系统必须保证移动端在本特性完成后不再持有用于直连底层文件服务或底层数据服务的业务调用路径
- **FR-015**: 系统必须为新增后端服务定义清晰的业务接口边界，使后续新增资料类型或业务模块时可以沿用相同模式扩展

### Key Entities *(include if feature involves data)*

- **移动端后端连接配置**: 移动端用于访问统一后端服务的连接信息，决定应用当前请求目标
- **后端业务接口**: 围绕资料、文件、提醒、协作、偏好等业务领域暴露的服务能力边界，向移动端提供稳定结果
- **文件性质资源结果**: 由后端整合后的保险合同、说明书等业务记录与其文件状态、下载能力、完整性状态等信息
- **非文件业务数据结果**: 由后端整合后的冰箱贴、备忘录、提醒、偏好和文档元数据等结构化业务结果
- **下游存储连接配置**: 后端用于访问底层文件服务和底层数据服务的目标信息，用于维持既有存储职责边界
- **业务操作结果**: 一次后端调用返回给移动端的统一结果，包含成功、失败、部分成功、资源缺失或待修复等可展示状态

## Assumptions

- 当前仓库已有移动端直连底层文件服务与底层数据服务的实现，本次工作需要将这些逻辑迁移到统一后端服务
- 当前文件服务与数据服务仍分别承担文件本体和结构化业务数据的正式存储职责，本次调整不改变这一边界
- 移动端依然保留本地用户偏好与敏感信息保存能力，但不再直接承担底层业务存储集成
- 为保持现有使用方式，移动端默认仍可在应用内修改自身连接目标；如需调整下游存储目标，也将通过后端能力完成
- 本次特性范围包括新增后端项目、迁移移动端集成逻辑、定义按业务拆分的后端接口，以及完成移动端对后端的新接入
- 本次特性不默认要求引入新的最终用户业务模块，而是以现有资料、提醒、协作、设置等模块的集成重构为主

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的移动端核心业务请求都通过统一后端服务完成，不再存在正式使用路径直接访问底层文件服务或底层数据服务
- **SC-002**: 用户在仅配置后端服务地址的情况下，能够完成资料列表查看、文件上传下载以及至少一类非文件业务数据的完整维护流程
- **SC-003**: 在后端服务可用的前提下，现有资料、提醒、协作与设置相关核心流程的主要结果与迁移前保持一致，且用户无需学习新的业务操作路径
- **SC-004**: 当后端下游任一存储服务不可用时，100% 的失败场景都能够向移动端返回明确可展示的业务结果说明
- **SC-005**: 搜索、提醒和资料详情等聚合场景能够通过单次后端业务结果满足移动端展示需要，减少移动端自行拼装多来源数据
- **SC-006**: 团队新增一个新的文件类或非文件类业务接口时，可沿用既有后端业务边界完成扩展，而无需重新引入移动端直连下游存储的模式

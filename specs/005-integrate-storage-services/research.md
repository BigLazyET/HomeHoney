# Research: 集成外部文件与数据存储

## 决策 1：将连接地址做成用户可编辑配置，但把“地址”和“敏感凭据”分开存储

- **决策**：文件服务基础地址、数据库主机/库名等非敏感配置由应用偏好持久化；密码、令牌或完整连接串中的敏感部分优先放入安全存储，并通过统一配置服务在运行时组装成最终连接信息。
- **理由**：用户明确要求后续能在 app 中人为修改和配置服务地址，但移动端直接把完整连接凭据写入普通 JSON 偏好文件会放大泄露风险。拆分存储既能满足可配置性，也能降低凭据暴露面。
- **考虑过的替代方案**：
  - **把完整地址和凭据都写入普通偏好文件**：被否决，因为不利于保护数据库凭据和 API 登录信息。
  - **完全写死到配置文件或源码**：被否决，因为不满足用户可修改连接目标的核心需求。

## 决策 2：在 UI 和外部服务之间增加应用服务 + 网关/仓储层，而不是让页面直接调用外部 API 或数据库驱动

- **决策**：Blazor 页面只调用应用层意图接口，例如“保存存储配置”“上传说明书文件”“查询提醒列表”；文件服务由专用 HTTP 网关适配，MongoDB 由专用仓储适配，跨两端的数据一致性由编排服务负责。
- **理由**：当前仓库已经采用服务层组织业务逻辑。继续沿用该模式可以把外部服务协议、认证、重试、DTO 映射和异常分类限制在基础设施层，避免页面直接依赖远端协议。
- **考虑过的替代方案**：
  - **页面直接调用 FileBrowser API**：被否决，因为会把 HTTP 协议、认证细节和错误处理扩散到组件层。
  - **页面直接使用 MongoDB Driver**：被否决，因为会让 UI 与数据访问强耦合，且不利于测试与未来替换实现。

## 决策 3：文件本体放外部文件服务，文件元数据和业务记录放 MongoDB，并通过文件引用关联

- **决策**：保险合同、说明书等文件性质资源拆分为“文件本体”和“业务元数据”两部分：二进制文件由文件服务托管，MongoDB 仅保存标题、分类、标签、关联成员、更新时间、文件引用、完整性状态等结构化字段；冰箱贴、备忘录、提醒、用户偏好等非文件数据直接保存在 MongoDB 集合中。
- **理由**：这与用户提出的职责分工完全一致，也符合现有模型中“文档元数据”和“附件数量”等字段独立存在的结构。
- **考虑过的替代方案**：
  - **把所有内容都放入 MongoDB**：被否决，因为用户明确要求文件资源放到文件服务中。
  - **把元数据也尽量塞进文件服务自定义字段**：被否决，因为会削弱查询、标签、提醒和业务关系建模能力。

## 决策 4：为跨文件服务与 MongoDB 的双写流程引入一致性状态，而不是假设两边永远同时成功

- **决策**：上传/删除/更新文件性质资源时，系统记录 `PendingUpload`、`PendingMetadataSave`、`Healthy`、`FileMissing`、`SyncError` 等一致性状态，并在 UI 中反映操作结果。
- **理由**：文件服务与 MongoDB 是两个独立远端系统，任何一次操作都可能出现“文件已上传但元数据未保存”或“元数据仍在但文件已丢失”的部分成功情形。若不显式建模，用户将无法理解系统实际状态。
- **考虑过的替代方案**：
  - **遇到失败就只弹一次通用错误**：被否决，因为无法支持后续修复、补偿或重试。
  - **要求两边必须强事务**：被否决，因为文件服务与 MongoDB 之间不存在天然分布式事务边界。

## 决策 5：为满足宪章的离线优先要求，引入本地 SQLite 缓存和本地文件缓存

- **决策**：尽管远端成为正式存储位置，应用仍保留本地 SQLite 元数据缓存、已下载文件副本和同步状态表，用于支持离线浏览、错误提示和后续同步恢复。
- **理由**：项目宪章明确要求核心数据本地可用。如果完全改为在线直连，规范将直接冲突。采用“远端主存储 + 本地缓存/同步层”可以在满足用户新需求的同时维持既有治理约束。
- **考虑过的替代方案**：
  - **完全在线模式**：被否决，因为违反离线优先原则。
  - **完整双向实时同步引擎**：暂不采用，因为超出本特性的必要范围；先实现缓存和明确的同步状态即可。

## 决策 6：MongoDB 接入采用仓储接口包裹直接驱动访问，并预留未来代理服务替换空间

- **决策**：当前特性按用户提供的本地 MongoDB 连接目标进行规划，但 MongoDB 驱动只能出现在基础设施仓储层，对上暴露的是领域仓储接口而非数据库细节。
- **理由**：用户当前已给出可用连接串，本地开发可直接接入；同时移动端直接暴露数据库连接存在长期安全与运维风险，因此必须把该决策局限在可替换的仓储边界内，后续若改为后端 API，不需要重写 UI 和领域服务。
- **考虑过的替代方案**：
  - **立即要求新增独立后端 API**：被否决，因为这超出当前用户范围说明。
  - **在所有服务中直接 new MongoClient**：被否决，因为会导致连接管理、测试替换和后续演进失控。

## 决策 7：列表页以业务元数据为主数据源，再按需补充文件可用性，而不是反过来从文件服务构造业务列表

- **决策**：资料列表、搜索结果、提醒来源等用户可见列表默认从 MongoDB 元数据查询，再结合文件引用状态显示“可下载 / 缺失 / 待同步”等文件状态；仅在真正上传、下载或查看文件属性时调用文件服务。
- **理由**：文件服务更适合管理二进制对象，不适合作为复杂业务列表、标签过滤和提醒关系的唯一来源。以 MongoDB 元数据为主，可以保持与现有文档模型一致。
- **考虑过的替代方案**：
  - **直接遍历文件服务目录生成列表**：被否决，因为不利于分类、标签、成员归属和提醒联动。
  - **每次列表都同时请求两端并强依赖两边成功**：被否决，因为会放大延迟和失败耦合。
